## 2. Java 项目：架构与实际价值

### 2.1 模块、依赖与通信

```text
直播平台 → WssBarrageServer.exe（实现源码未见）
          → ws://127.0.0.1:8888
          → BarrageClientService（Type=1，Data 二次 JSON，昵称+Content）
          → GameService（限频、去重、点积打分、回合与胜负）
             ├ VectorService ← ../vectors/vectors.json + ../common_words.txt
             ├ PinyinService
             ├ JPA → SQLite ./data/game.db
             └ STOMP /topic/game → SockJS /ws/game → Zustand → React 页面
浏览器初始化另用 HTTP /api/room/status、/leaderboard、/dimensions
```

源码事实：后端 Spring Boot **3.2.0**、Java **17**、SQLite JDBC **3.42.0.0**、pinyin4j **2.5.1**；Web、WebSocket、JPA、Jackson 由 Boot 依赖管理。[J-deps]

前端声明 React ^18.2.0、Zustand ^4.4.7、Chart.js ^4.4.1、react-chartjs-2 ^5.2.0、STOMP ^7.0.0、SockJS ^1.6.1、Vite ^5.0.8；锁文件实际锁为 React/ReactDOM **18.3.1**、Zustand **4.5.7**、Chart.js **4.5.1**、react-chartjs-2 **5.3.1**、STOMP **7.3.0**、SockJS **1.6.1**、Vite **5.4.21**、React Vite 插件 **4.7.0**。[J-lock-stomp] [J-lock-plugin] [J-lock-chart] [J-lock-react] [J-lock-sockjs] [J-lock-vite] [J-lock-zustand]

后端端口 8080；开发前端端口 3000、监听 0.0.0.0，以 Vite 代理 /api、/ws 到本机后端。STOMP 内存 broker，仅 /topic；未见分布式消息或多房间分区。[J-yml] [J-vite] [J-wsconfig]

实际价值：把观众的两字词即时转为“距离答案有多近”的可视反馈，用排行、渐进提示、自动换局延长共同解题过程。它是可研究的玩法实现，不能因作者描述直接认定已经具备可复制的获客或变现效果。

### 2.2 角色、用户故事与完整操作链

| 角色 | 实际故事与实现边界 |
| --- | --- |
| 主播/运行者 | 准备向量与常用词表、启动桥接/后端/前端，把网页作为直播画面；后端启动自动建局。当前 React 首页没有房间连接设置、人工出题、暂停、手动换题或运行健康面板。[J-init] [J-app] |
| 观众 | 在弹幕发送恰好两个中文字符；桥接客户端只接受 \u4e00–\u9fa5 范围的两字文本，每昵称10秒最多3次；合格输入立即参与语义打分。没有稳定平台用户ID，昵称即身份。[J-barrage] [J-parser] [J-rate] |
| 共同解题者 | 新词进入历史排行；重复词仅出现在弹幕并标次数，不再计总次数、不再评分/记录玩家贡献；词库外显示“不在词库”。[J-submit] |

| 回访观众 | 排行按累计胜场；提交记录、玩家胜场与游戏结果写 SQLite；重启会开新局，未见恢复未结束回合/上局前端状态。[J-persist] [J-leader] |

### 2.3 页面、视觉元素与交互

只有一张活动 React 页面，没有路由式管理后台与观众页面分离。

1. 顶栏：标题“猜词游戏”、规则文案、主题切换；猜中后获胜横幅与答案。
2. 上部：左侧上一局结果卡、实时弹幕卡；右侧奖牌排行（昵称、胜场、前三差异高亮）。
3. 主体：历史猜测卡、N/120徽标和进度、拼音提示、最新猜测闪亮状态；去重后按相似度降序，猜中优先、词库外末尾。
4. 十维雷达作为历史区背景水印，维度为食物/学习/游戏/科技/艺术/自然/情感/运动/动物/生活；活动页面实际只画目标词，并非同时叠加最新猜词。目标画像值乘2、刻度上限1，会造成高值裁切。
5. 相似度≥0.6提示“接近了”、≥0.8提示“就差一点”，3秒消失。实时弹幕区域是纵向列表自动滚到底，不是横向飞屏。
6. CSS 固定1080宽、最小1920高，适合作为竖屏直播设计原型，但没有验证不同 OBS 裁切、手机安全区及实际字体大小。

以上分别见 [J-ui-layout] [J-history] [J-danmaku-ui] [J-css]。

实际主题字典有 **16** 个具名条目（10浅色+6直播），并非作者资料所述17。最后六个为直播白/黑/蓝/紫/红/绿。themeStore 未用持久化 middleware/localStorage；刷新后主题恢复默认。[J-theme-start] [J-theme-live]

可借鉴：竖屏单一焦点、进度/距离并列、历史词排行、目标画像水印、短时热度提示、上局获胜者荣誉展示。数字“关联度”只是模型分数，不是概率；十维锚点画像也不等于科学测得的人类语义结构。

### 2.4 数据、打分与关键缺口

| 核查项 | 源码事实 → 对落地的影响 |
| --- | --- |

## 3. Python 桌面项目：架构与实际价值

### 3.1 模块与依赖

```text
main.py → load_model → SentenceTransformer(BGE) → 10维锚点画像初始化
       → QApplication（全局主题）
          ├ MainWindow 主播台 → engine（共享内存状态+锁）
          └ LiveWindow 直播大屏 ← 每秒get_state轮询
engine ← wordbank（10类80条题）+ similarity缓存
礼物操作 → ScoreWorker(QThread) → submit_batch → UI信号刷新
LiveWindow → RadarChart + DanmakuStrip + AssociationBoard + ScoreBoard
theme.json：仅主题持久化；crash.log：崩溃日志
```

实际 requirements.txt仅声明 **PyQt6>=6.6**；sentence-transformers>=2.2被注释，torch也不在依赖清单。README要求Python3.11+、torch、sentence-transformers；main强制加载BGE，缺失则退出。**按README单独安装requirements再运行下载脚本，在干净环境会缺sentence_transformers**。build.bat另安装未固定版本的PyQt6/sentence-transformers/PyInstaller，因此构建也没有可复现的完整版本锁。[P-req] [P-readme-env] [P-main] [P-build]

模型为 `BAAI/bge-small-zh-v1.5`；先找项目models/bge，再找PyInstaller _MEIPASS目录，否则按模型名联网下载。README明确不随仓库提供。未锁模型revision或记录hash，首次联网、获取完整模型与离线打包均是前置条件；本次未下载。[P-model] [P-download] [P-readme-model]

### 3.3 页面与视觉：可借鉴细节

**主播台（1100×720）**：顶部标题、直播开关与11主题下拉；当前谜底/词性、上局冠军；时间进度条和秒数、提示锁；中间3:2关联度榜与积分榜；底部昵称/猜词输入、礼物类型和送出、分类/难度筛选、抽题/手动出题、两种重置及状态文案。谜底和出题成功状态都直接显示，因此OBS不可捕获此窗口。[P-main-layout] [P-main-actions] [P-puzzle-actions]

**直播大屏（960×680）**：顶部“？？”谜底牌、LIVE红标、进度和大号剩余时间、文字提示与拼音；其下飞过弹幕条；中部左关联度榜、右雷达和积分榜；底部全屏/无边框/主题工具条。普通局始终遮罩文字答案，solved才显示；超时仍显示“？？”而非揭晓。[P-live-init] [P-mask]

**表现与可复用思路**：

- 猜中庆祝是半透明全屏遮罩、白色圆角卡、获胜者大字、答案72px，30ms定时淡入+轻缩放。[P-congrats] [P-anim]
- 关联度榜含昵称、词、礼物标记、合并次数、0–100渐变进度条、一位小数；按词复用控件并只在排序变更时重排。不是每秒重建整榜。[P-assoc]
- 积分前三固定金卡，第4名以后滚动；复制两份列表实现循环。更新积分时仍会重建后半榜，与README“任何刷新不得重建”绝对表述不同，不能仅凭说明认定完全无闪烁。[P-scoreboard]
- 雷达目标浅色填充、猜词亮色描边，十轴与四层网格。但LiveWindow传入的是**本局最佳真实猜词best_word**，不是注释/README说的最新猜词。[P-radar] [P-radar-data] [P-best]
- 接近55/75时横幅“接近了/就差一点”，2.6秒收回；每局每个词飞屏一次，上限14条，30ms移动。[P-prox-constants] [P-prox-ui] [P-danmaku]
- 11套主题=6浅色+5深色直播主题；主题同步两个窗口并存theme.json。源码有固定绿色/白色内联样式，故并非所有元素完全跟随深色主题，需要真实OBS画面验证。[P-theme] [P-theme-persist] [P-mask]
- 拼音提示按“距离文本提示解锁时间”的40%先揭首字首字母、70%揭全部；默认hint_time120秒即48/84秒，并非总时长240秒的40%/70%；pypinyin缺失时无提示且安装清单未声明。[P-pinyin]

十维画像另有口径差异：Python先单位化每个锚点嵌入再求均值，没有把均值向量再次单位化，所以画像值是对该维锚点相似度的平均，并非严格的“与单位维度基向量的余弦”。Java会将锚点均值再次归一化，两套画像的数值不能直接横比。见 [Python画像公式](https://github.com/LiMCZJY/semantic-guessword/blob/938d16a6fd79337b9784dcfa55a432b94cd27781/semantic.py#L46-L104) 与 [J-vector-score]。

### 3.4 打分、回合、持久化与落地阻塞

| 项 | 源码事实与结论 |
| --- | --- |
| 正常分数 | BGE encode(normalize_embeddings=True)，点积等价单位向量余弦；默认cos口径负值归零；shift为可选口径，不能跨口径复用热度阈值。打分不是校准概率。[P-score] |
| 判胜 | 使用四舍五入后sc>=100，而非最终再次比较词语；推断：不同字符串若模型相似度极接近1并被四舍五入100，也可能被判猜中。应把精确命中与关联度展示分离。[P-score] [P-scoring] |
| 模型推理与UI | 手动submit_guess在GUI线程同步推理；只有礼物批次放QThread。雷达未缓存词第一次profile也在UI刷新内算。启动模型在创建QApplication前，无GUI加载进度。不能以有worker就认定全流程不卡。[P-main] [P-submit-ui] [P-radar-data] |
| 回合竞态 | submit_batch锁外按当前state.answer逐词算分，入锁后仅看当前局是否ended，不校验计算时round_id。主播随时可new_round；推断旧礼物批次可混入新局。缓存、模型实例也由UI与worker共享，未见专用推理队列/模型互斥。[P-batch] [P-newround] |
