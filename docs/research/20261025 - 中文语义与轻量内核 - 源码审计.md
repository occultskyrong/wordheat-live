## 2. Chinese Semantle

### 2.1 技术架构和依赖

前端是原生 HTML + CSS + JavaScript，无前端框架/打包器依赖清单。页面通过 Fetch 调 FastAPI；localhost 默认指向 8000，其余默认同源，可通过 `window.SEMANTLE_API_BASE` 覆盖。[前端入口](https://github.com/ispacekid/chinese-semantle/blob/9313d3a340eb61d28d55b002ee0cd06afbe355b7/frontend/app.js#L14-L22)

后端为 Python 3.11（Docker 基础镜像）、FastAPI 0.115.0、Pydantic 2.9.2、PyYAML 6.0.2；本地完整依赖加 Uvicorn 0.31.0、gensim 4.3.3、numpy <2.0；精简运行依赖含 asyncpg 0.29.0。QQ Bot 独立依赖 qq-botpy >=1.2.1、httpx >=0.27.0、PyYAML >=6.0.1，未锁定精确版本。[运行依赖](https://github.com/ispacekid/chinese-semantle/blob/9313d3a340eb61d28d55b002ee0cd06afbe355b7/requirements.txt#L1-L10)、[本地依赖](https://github.com/ispacekid/chinese-semantle/blob/9313d3a340eb61d28d55b002ee0cd06afbe355b7/backend/requirements-local.txt#L1-L6)、[Bot 依赖](https://github.com/ispacekid/chinese-semantle/blob/9313d3a340eb61d28d55b002ee0cd06afbe355b7/qqbot/requirements.txt#L1-L4)

### 2.2 中文评分：三个引擎不是同一种体验

| 引擎 | 数据与行为 | 对直播体验的影响 |
|---|---|---|
| Local | gensim KeyedVectors 加载腾讯中文词向量；两词皆存在时计算真实余弦；Top-K 用 `most_similar`，不含自身 | 可以给词表内冷词连续反馈；词表外不能算。每次开局计算近邻，内存、首局耗时待测 |
| Light | 读取 `neighbors.sqlite`；`has()` 只看所有谜底邻居并集或谜底；`similarity(target,guess)` 只查目标的预计算邻居，不在该表返回 -1 | 某词可被接受，却因为不在当前题 Top3000 得不到真实分数；大量冷词并列，削弱“越来越近”的探索反馈 |
| Mock | 缺原始向量或 gensim 等依赖时可回落；2–4 字纯汉字可通过词校验，以 Python hash 产生伪分数 | 仅适合界面联调；无语义意义，Python hash 默认还可能跨进程变化。不能用于任何正式游戏 |

`SEMANTLE_ENGINE=auto`（缺省）优先 Light，缺数据库才回 Local；显式 `local` 缺数据仍可能回 Mock，显式 `light` 缺数据抛异常。不能用“接口能启动/health ok”证明真模型已就绪。[选择顺序](https://github.com/ispacekid/chinese-semantle/blob/9313d3a340eb61d28d55b002ee0cd06afbe355b7/backend/app/engine_base.py#L59-L111)、[Local 余弦与近邻](https://github.com/ispacekid/chinese-semantle/blob/9313d3a340eb61d28d55b002ee0cd06afbe355b7/backend/app/engine.py#L126-L142)、[Mock 实现](https://github.com/ispacekid/chinese-semantle/blob/9313d3a340eb61d28d55b002ee0cd06afbe355b7/backend/app/engine.py#L274-L350)、[健康检查](https://github.com/ispacekid/chinese-semantle/blob/9313d3a340eb61d28d55b002ee0cd06afbe355b7/backend/app/main.py#L250-L252)

Top3000 的具体结果：API 将余弦乘 100，Light 未命中得到 -100；Web 已把负数显示为“低相似度”，所以界面不是直接展示 -100，但冷词无法按真实语义远近排序。这是评分信息丢失，不只是文案问题。Light 的查询还是以谜底为第一参数查缓存，不能把其接口当通用、对称的任意词对相似度服务。[Light 语义契约](https://github.com/ispacekid/chinese-semantle/blob/9313d3a340eb61d28d55b002ee0cd06afbe355b7/backend/app/engine_light.py#L26-L33)、[查询实现](https://github.com/ispacekid/chinese-semantle/blob/9313d3a340eb61d28d55b002ee0cd06afbe355b7/backend/app/engine_light.py#L204-L243)、[API 分数](https://github.com/ispacekid/chinese-semantle/blob/9313d3a340eb61d28d55b002ee0cd06afbe355b7/backend/app/game.py#L212-L241)、[Web 低相似度展示](https://github.com/ispacekid/chinese-semantle/blob/9313d3a340eb61d28d55b002ee0cd06afbe355b7/frontend/app.js#L636-L640)

注释曾称“懒装载、<100MB”，实际 `_load_known_words` 启动扫描全部 blob、解压并保留两套邻居缓存。README 写 Light 约 1GB / 4 秒，Compose 配 1200M；这些是作者文档与资源配置，不是本次测得性能。方案容量预算不能沿用旧注释的 <100MB。[全量装载](https://github.com/ispacekid/chinese-semantle/blob/9313d3a340eb61d28d55b002ee0cd06afbe355b7/backend/app/engine_light.py#L129-L160)、[资源配置](https://github.com/ispacekid/chinese-semantle/blob/9313d3a340eb61d28d55b002ee0cd06afbe355b7/docker-compose.yml#L35-L42)

另一个规则一致性问题：页面写“#1 即谜底本身”；实际 rank_map 从不含自身的邻居直接 enumerate +1，猜中靠字符串相等判定，前端另造一条 `proximity_rank:1` 的成功展示。因此 API 最近邻 #1 与谜底成功态 #1 不是同一套严谨排名。新方案应统一为“答案命中独立标识；相关词第1名另算”或将答案纳入候选集后统一排名。[玩法文案](https://github.com/ispacekid/chinese-semantle/blob/9313d3a340eb61d28d55b002ee0cd06afbe355b7/frontend/index.html#L69-L86)、[rank_map](https://github.com/ispacekid/chinese-semantle/blob/9313d3a340eb61d28d55b002ee0cd06afbe355b7/backend/app/game.py#L97-L102)、[成功展示](https://github.com/ispacekid/chinese-semantle/blob/9313d3a340eb61d28d55b002ee0cd06afbe355b7/frontend/app.js#L695-L706)

### 2.3 词库和模型是否包含

固定树包含 `target_words.txt`（1781 个非注释词）、`puzzle_codes.json`（1781 条 code→word）、78,405,632 字节 `neighbors.sqlite`；不包含原始腾讯 `.bin/.txt` 向量或 gensim `.kv`。1781 是本次读取小型词表/JSON 解析计数；没有下载 SQLite，数据库实际每条 Top-K 内容未做二进制检验。

谜底池来自人工 whitelist，构建脚本校验 2–4 字、纯汉字、向量内存在，不是脚本自动证明“常用、客观、适合直播”。`is_common` 本质是白名单成员测试。提示优先白名单，找不到可退化到其他邻居；因此仍需人工抽题、近邻审查。[词库构建规则](https://github.com/ispacekid/chinese-semantle/blob/9313d3a340eb61d28d55b002ee0cd06afbe355b7/backend/scripts/build_wordlist.py#L1-L16)、[词库](https://github.com/ispacekid/chinese-semantle/blob/9313d3a340eb61d28d55b002ee0cd06afbe355b7/backend/data/target_words.txt)、[预计算生成](https://github.com/ispacekid/chinese-semantle/blob/9313d3a340eb61d28d55b002ee0cd06afbe355b7/backend/scripts/build_precomputed.py#L105-L154)

### 2.6 防泄题、防伪与运行阻塞

1. **HMAC 不是保密方案。** 六位编号通过HMAC生成，但公开仓库直接提交1781条 code→word 反向JSON；SQLite结构也明文存 target。沿用公开数据与编号可以被查表。若更换密钥，必须同时重建数据库code和反向表；只改运行环境密钥会使 `encode_word(target)` 与既有cache键失配。[编码与反向表](https://github.com/ispacekid/chinese-semantle/blob/9313d3a340eb61d28d55b002ee0cd06afbe355b7/backend/app/puzzle_codes.py#L39-L89)、[公开映射](https://github.com/ispacekid/chinese-semantle/blob/9313d3a340eb61d28d55b002ee0cd06afbe355b7/backend/data/precomputed/puzzle_codes.json)、[SQLite schema](https://github.com/ispacekid/chinese-semantle/blob/9313d3a340eb61d28d55b002ee0cd06afbe355b7/backend/scripts/build_precomputed.py#L85-L97)
2. **前端隐藏不能约束观众。** `hint=0/giveup=0`只控制JS按钮；后端hint/giveup未读取出题者禁用政策。公开encode又可作为词到编号查询；合法题还可按code另开一局放弃揭晓。主播保密题不能只靠关按钮/隐藏答案DOM。[前端能力开关](https://github.com/ispacekid/chinese-semantle/blob/9313d3a340eb61d28d55b002ee0cd06afbe355b7/frontend/app.js#L489-L527)、[后端提示/放弃](https://github.com/ispacekid/chinese-semantle/blob/9313d3a340eb61d28d55b002ee0cd06afbe355b7/backend/app/main.py#L367-L397)
3. **排行榜防伪范围有限。** token签入题号/次数/game_id/一小时过期并验HMAC，能防直接篡改次数；未见一次性消费、game_id唯一约束或提交去重，Repo只append/INSERT，可重复提交同一个有效token。创建请求还接受`hint_count=0..10`初始提示，Game构造时`hint_ever_used`仍为False，故随机局可先得到初始提示但仍满足当前计分条件（静态调用链发现，未运行验证）。没有身份认证、房间参赛约束、限频机制；知道答案后刷随机题的“合法一猜”也不靠签名解决。未发起实际攻击。[token](https://github.com/ispacekid/chinese-semantle/blob/9313d3a340eb61d28d55b002ee0cd06afbe355b7/backend/app/leaderboard/tokens.py#L66-L125)、[初始提示参数](https://github.com/ispacekid/chinese-semantle/blob/9313d3a340eb61d28d55b002ee0cd06afbe355b7/backend/app/models.py#L53-L55)、[提示构造与标记](https://github.com/ispacekid/chinese-semantle/blob/9313d3a340eb61d28d55b002ee0cd06afbe355b7/backend/app/game.py#L103-L129)、[提交接口](https://github.com/ispacekid/chinese-semantle/blob/9313d3a340eb61d28d55b002ee0cd06afbe355b7/backend/app/main.py#L568-L596)、[表与插入](https://github.com/ispacekid/chinese-semantle/blob/9313d3a340eb61d28d55b002ee0cd06afbe355b7/backend/app/leaderboard/repo.py#L128-L181)

## 3. Quid

### 3.1 架构、模型与依赖

纯原生ES module JS + HTML/CSS，使用仓库内 `idb-keyval.js` 持久化状态、`haptic.js` 触觉反馈、Service Worker缓存和PWA manifest；没有Node服务、账号库或远端评分API。Go脚本是离线裁词/量化工具，运行网页不需要Go。没有package.json或npm版本锁定，不能按React/Vue项目估算接入成本。[模块入口](https://github.com/rberenguel/quid/blob/357285d2d9638314b5540326d0cd261b540c1530/script.js#L1-L8)、[量化结构](https://github.com/rberenguel/quid/blob/357285d2d9638314b5540326d0cd261b540c1530/reducers/pruner.go#L14-L21)

README部分文案仍写GloVe，但Under the Hood和Credits已改fastText；实际语言配置为ca/de/en/es/fr/it，引用六个 `cc.<lang>.50.txt.quantized.json`，没有中文配置/模型。文件名为50维，实际解码按JSON `dimension/min/max`；本次未读取8–11MB的模型大文件，未独立验证模型内部词数和真实维度。README的“50,000词、50维”可作为作者声明，不能写成本次实测。[模型配置](https://github.com/rberenguel/quid/blob/357285d2d9638314b5540326d0cd261b540c1530/script.js#L10-L55)、[实际解码](https://github.com/rberenguel/quid/blob/357285d2d9638314b5540326d0cd261b540c1530/script.js#L407-L470)、[说明中的更新与旧文案](https://github.com/rberenguel/quid/blob/357285d2d9638314b5540326d0cd261b540c1530/README.md#L45-L66)

启动下载当前语言模型，分块反量化，然后对全部候选与谜底算余弦、全量排序建立名次。猜词时查已算表，反馈快；首次下载、JS对象内存、排序卡顿与移动设备耗电仍待实机测量。词表只支持固定条目；尽管原始fastText二进制支持子词/OOV，这里是导出的词向量JSON，并未运行完整fastText推断。[初始化路径](https://github.com/rberenguel/quid/blob/357285d2d9638314b5540326d0cd261b540c1530/script.js#L330-L395)

### 3.3 真实价值、部署与阻塞

- **客户端答案公开是设计前提。** appState有secretWord/secretVector，保存时又把secretWord明文放入IndexedDB；完整候选向量/排名可在本机检查。可做离线自玩或主播本机演示，不能把这个浏览器当无信任参赛客户端。[状态](https://github.com/rberenguel/quid/blob/357285d2d9638314b5540326d0cd261b540c1530/script.js#L57-L79)、[答案持久化](https://github.com/rberenguel/quid/blob/357285d2d9638314b5540326d0cd261b540c1530/script.js#L136-L165)
- **PWA不是零成本离线。** SW安装清单一次缓存六种语言模型，固定树六文件总量约53.1MB（不含其它资源）；`style.css`不在预缓存列表，fetch兜底网络又不写缓存，断网全新冷开可能缺样式。SW安装失败被catch记录，不能仅见注册逻辑就认定完整离线已验收。[SW清单与fetch](https://github.com/rberenguel/quid/blob/357285d2d9638314b5540326d0cd261b540c1530/sw.js#L1-L76)。页面使用ES modules、fetch、IndexedDB，宜静态HTTP(S)托管；PWA/SW需安全上下文，不适合双击file://作为正式部署方式。
- **中文迁移不是只加语言选项。** 需有合法中文向量和词库、输入法适配、常用词池、短语/繁简/异体处理、重新评估量化损失和近邻质量；要直播竞赛还需把答案、评分、房间和成绩移到服务端。
- **代码MIT已确认。** 保留版权及许可即可按MIT条款复用代码；模型许可另算。作者声明fastText来源，而fastText官方Common Crawl/Wikipedia词向量为CC BY-SA 3.0，不能把代码MIT套到派生量化模型上；还需核对确切源模型、修改说明与分发义务。仓库字体也应逐项核许可，不能自动随代码MIT放行。[MIT文件](https://github.com/rberenguel/quid/blob/357285d2d9638314b5540326d0cd261b540c1530/LICENSE#L1-L21)、[fastText官方词向量许可](https://fasttext.cc/docs/en/crawl-vectors.html#license)

## 4. 统一中文评分：三种可选路线

以下是方案建议，不是已完成模型比较。所谓“语义近”应先定义为中文词/短语关联度游戏；同义词、上下位、同场景词、反义词可能在不同模型下都很近，向量并不理解规则真伪，也不能证明百科事实。

| 路线 | 实施口径 | 优点 | 主要代价/边界 |
|---|---|---|---|
| A. 静态中文词向量，服务端完整余弦 | 确认许可与版本的腾讯/其他中文词向量；题库与猜词库固定；每个合法猜词都算真实余弦，Top-K只限制名次显示 | 贴近Semantle词语联想；词向量预载后查询路径简单；易缓存和复现 | 词库外处理弱；来源许可与版本要补；大向量内存待测；近义/反义混淆要审题 |
| B. BGE-small-zh-v1.5，统一服务端编码 | 谜底与猜词同一模型/同一预处理、都不加检索instruction；归一化后点积得余弦；候选池离线预编码 | 官方中文模型、模型卡MIT；可编码未列词短语，覆盖比固定词表灵活；可先作为首轮质量基线 | 单词任务效果不由句子检索榜单保证；中文短词需实测；延迟/内存不做承诺；开放任意短语会增加刷分与审核难度 |
| C. 固定中文猜词库，服务端全量预计算 | 选定A或B，离线为全部题库×允许猜词库建立真实分数/排名；服务端按题号查表；观众不下载答案映射 | 在线耗时稳定、易复盘；统一裁决，无模型服务冷启动；适合首版有界直播题库 | 存储随题数×词数增长；只能接收白名单词或明确走同模型在线补算；更新需整批版本化，不能像Light用-1冒充冷词分数 |

推荐先以BGE-small建立可复现实验基线，并让A做词语联想对照，最后按人工题库质量、冷词梯度、P95延迟与资源决定A/B；若首版直播只做少量审定题，可优先采用C的部署形态。不要将不同模型的原始分数混在一个榜里，也不要让LLM临场自由打分决定奖金/排名。

### 4.1 BGE官方资料支持什么

官方模型卡列 `bge-small-zh-v1.5` 为中文embedding模型并标MIT；建议对非“短query检索长passage”任务直接使用原文本；本方案是对称词/词短语相似任务，因此答案与猜词使用同一无instruction编码口径。若将来做“观众描述找词条解释”，才单独评估检索instruction及query/passage不对称设计。[BAAI模型卡](https://huggingface.co/BAAI/bge-small-zh-v1.5#model-list)

官方FAQ指出绝对余弦值依赖训练分布，大于0.5不自动代表语义相近，阈值应根据业务数据校准。因此余弦×100只能叫相似度显示值，不能叫“正确概率/懂了百分之几”。同样，C-MTEB或检索成绩不能证明本游戏中文短词好玩；性能只列待测项。[官方相似度与instruction FAQ](https://huggingface.co/BAAI/bge-small-zh-v1.5#frequently-asked-questions)

### 4.2 校准、精确命中和一致性验收

建议预备至少一批人工审定题，覆盖同义词、同场景、上下位、反义、多义、谐音、同字不同义、专名、错别字、无关词；给出期望相对顺序而非编造“应得83分”。测试同词精确命中、交换两词的对称性、同词重复评分、重启后复现、批量与单条一致、模型升级排名变化、人工认为冷/暖/热的分布。提示词另审可读性与泄底程度。

精确胜利优先用规范化后的明确答案/人工别名匹配；高相似分不自动算猜中。繁简、大小写、空格、标点、数字同形、别名是否同答案应逐项定规则，不能悄悄折叠。显示温度可以按固定候选词库的排名/分位校准；分位表示相对该词库的位置，也不是答对概率。低分/词库外/系统失败分开返回，不用伪分数掩盖失败。

### 4.3 版本和缓存键建议

维护一份immutable评分清单：`model_id + model_revision_sha + tokenizer_revision + pooling + normalize_embeddings + instruction_policy + precision/quantization + preprocessing_version + guess_lexicon_sha + target_pool_sha + ranking_policy + calibration_version`。模型卡MIT与词库来源许可也随清单留档。

单词向量缓存键用“评分清单hash + 规范化词”；词对原始相似度缓存仅在确认对称时按词对排序；排名/提示缓存还要带题目ID、猜词库SHA、提示算法版本；回合结果带房间ID/round_id与冻结评分清单hash。不同模型/精度/词库/校准版本不互用缓存；变更密钥与评分版本是两件事，不用改密钥去表达模型升级。

首版可复现实验需要报告：模型/词库许可来源、中文基线样本与盲评结果、冷词信息量、精确命中规则、失败返回、首次加载与P50/P95/P99延迟、并发去重与批量策略、峰值RSS、量化前后排名差、重启恢复和防泄题路径。当前源码研究尚不提供这些运行验收数据。
